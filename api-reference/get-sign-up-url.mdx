title: "getSignUpUrl — Generate a PKCE Sign-Up URL for AuthKit"

description: "getSignUpUrl returns a WorkOS AuthKit authorization URL and cookie headers for PKCE-secured sign-up. Forward both url and headers in your Remix redirect response."
---

`getSignUpUrl` works identically to [`getSignInUrl`](/api-reference/get-sign-in-url) but sends `screenHint: 'sign-up'` to WorkOS, which instructs AuthKit to present the registration UI first rather than the sign-in form. Like `getSignInUrl`, it generates a PKCE code verifier, stores it encrypted in a short-lived HttpOnly cookie, and returns a `{ url, headers }` object — both must be forwarded to start a secure sign-up flow. Use `getSignUpUrl` in a dedicated Remix loader and redirect the user immediately.

## Import

```typescript
import { getSignUpUrl } from '@workos-inc/authkit-remix';
```

## Signature

```typescript
getSignUpUrl(returnPathname?: string, request?: Request): Promise<GetAuthURLResult>
```

## Parameters

<ParamField path="returnPathname" type="string" optional>
  The pathname to redirect the user to after they successfully authenticate. Must be a same-origin pathname (e.g. `"/welcome"`). Paths longer than 1 KiB in JSON representation are silently omitted; the callback will fall back to its configured `returnPathname` or `/` in that case.
</ParamField>

<ParamField path="request" type="Request" optional>
  The incoming Remix `Request` object. Providing the request is strongly recommended: it allows the SDK to detect and prune stale PKCE cookies from previous abandoned flows (preventing HTTP 431 errors when five or more flow cookies accumulate), and it ensures cookie security attributes (e.g. `Secure`) correctly reflect the actual request protocol. Behind a TLS-terminating proxy, configure the proxy to set `X-Forwarded-Proto` to the trusted client-facing scheme.
</ParamField>

## Return value

`getSignUpUrl` returns a `Promise<GetAuthURLResult>` — an object with the following fields:

<ResponseField name="url" type="string">
  The complete WorkOS AuthKit authorization URL to redirect the user to. The URL contains only a random state nonce; the PKCE verifier and return pathname travel exclusively in the cookie.
</ResponseField>

<ResponseField name="headers" type="Headers">
  A `Headers` instance that **must** be forwarded on the redirect response. It contains one or more `Set-Cookie` directives: the new PKCE flow cookie and, when stale flow cookies were pruned, their deletion directives. Omitting these headers will cause the callback to fail.
</ResponseField>

## Usage

Create a dedicated sign-up route and immediately redirect to the authorization URL, forwarding `headers`:

```typescript
// app/routes/sign-up.ts
import { redirect, type LoaderFunctionArgs } from '@remix-run/node';
import { getSignUpUrl } from '@workos-inc/authkit-remix';

export async function loader({ request }: LoaderFunctionArgs) {
  const { url, headers } = await getSignUpUrl('/welcome', request);
  return redirect(url, { headers });
}
```

Link to this route with a plain anchor element or `<Link reloadDocument>` — do not use Remix's default client-side prefetch:

```tsx
<a href="/sign-up">Create account</a>
```

## Important notes

- **The result is not a plain string.** `getSignUpUrl` returns `{ url, headers }`, not a URL string. Destructure the object before passing to `redirect`.
- **Always forward all headers on the redirect response.** The `headers` value may contain multiple `Set-Cookie` directives, including cookie deletions. Forwarding only `url` will cause the callback to fail with a missing-cookie error.
- **Never serialize the result into loader JSON data.** Do not `return { url, headers }` from a loader for the browser to consume — `headers` is a `Headers` instance and cannot be serialized, and the PKCE state must not be exposed to the client.
- **Use a dedicated route.** Avoid generating sign-up URLs in every page loader. Calling `getSignUpUrl` starts the ten-minute login window and creates a flow cookie; doing so on every page render accumulates unused cookies and wastes the login window.
- **Do not prefetch this route.** Remix's `<Link prefetch>` and related APIs would trigger the loader without any user intent, starting the login window unnecessarily.

<Note>
  `getSignUpUrl` and `getSignInUrl` are functionally identical in their PKCE and cookie mechanics. The only difference is the `screenHint` value sent to WorkOS: `'sign-up'` causes AuthKit to render the registration form first, while `'sign-in'` renders the login form first. Users can still navigate between the two screens within AuthKit regardless of which hint is provided.
</Note>

<Warning>
  During a rolling deployment you must deploy the sign-up initiation helpers and the callback route handler together on all instances simultaneously. Old in-flight sign-up flows that lack the new PKCE browser cookie will intentionally fail closed. Do not run old and new handler versions side-by-side — users with in-flight sign-up flows at the moment of the cutover will need to restart. Existing authenticated sessions are not affected.
</Warning>
